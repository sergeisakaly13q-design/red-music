# Red Music — версия 4.1 (реальный backend, SQLite)

## Что изменилось в 4.1
браузера (см. историю версий 3.x ниже) — фактически данные не были общими и
пропадали при очистке браузера. Теперь добавлен настоящий backend:

- **База данных** — SQLite (обычный файл `data/red-music.db`, создаётся
  автоматически при первом запуске, **никаких аккаунтов/установок не нужно**).
  Хранит пользователей, роли, треки, историю прослушивания, журнал действий,
- **Авторизация** — пароли хранятся хешированными (bcrypt), сессия — через
  JWT в httpOnly-cookie.
- **Роли** — USER / VIP / CO-CREATOR / OWNER + кастомные роли, назначаются
  через API (`/api/roles`), ID 1 и ID 2 закреплены как OWNER — как и раньше.
- **Музыка** — загрузка файлов (`POST /api/music/upload`, до 25 МБ, mp3/wav/ogg/m4a/flac),
  стриминг (`GET /api/music/:id/stream`), избранное.
- **История прослушивания** — `POST /api/history`, `GET /api/history`.
- **Журнал действий (audit log)** — все ключевые действия (вход, регистрация,
  доступны через `GET /api/admin/logs` (только OWNER/CO-CREATOR).

**Важно:** сам файл `public/index.html` (весь интерфейс) пока не тронут — он
всё ещё работает по-старому, через `localStorage` (демо-режим). Новый backend
уже полностью готов, но подключение конкретных кнопок интерфейса к этим API —
следующий шаг. Старые/неиспользуемые файлы не удалены, а помечены `.bak`:
`server.legacy-static-only.js.bak`, `package.legacy.json.bak`, `README.legacy.md.bak`,
`db/pool.postgres-unused.js.bak` (первая версия backend'а была на PostgreSQL —
оставлена на случай, если позже понадобится вместо SQLite на проде).

## Локальный запуск (Windows / PowerShell)
Никаких внешних сервисов и регистраций не требуется:
1. `npm.cmd install`
2. `npm.cmd start`
3. Откройте http://localhost:3000 — при первом старте файл `data/red-music.db`
   создастся автоматически со всеми таблицами.

Если увидите в консоли `[db] SQLite схема применена/проверена: ...` — всё
подключилось правильно.

## Деплой на Render
1. Залейте проект в GitHub-репозиторий.
2. На Render: **New → Blueprint**, укажите репозиторий — `render.yaml` уже
   в проекте.
3. **Важно про хранение:** бесплатный план Render использует эфемерный диск —
   файл БД (`data/red-music.db`) и загруженная музыка (`uploads/`) пропадут
   при следующем деплое/рестарте. Варианты:
   - подключить платный **Persistent Disk** (уже настроен в `render.yaml` —
     монтируется в `storage/`, где лежат и БД, и музыка — но сам диск платный,
     это тариф Render, а не что-то, что можно включить бесплатно);
   - или переключить БД на управляемый PostgreSQL от Render (у нас уже есть
     готовая версия на Postgres в `.bak`-файлах — могу переключить обратно
     одной командой, если решишь использовать её на проде вместо SQLite);
   - или хранить музыку во внешнем облаке (S3, Cloudinary) — помогу добавить
     отдельным шагом.
4. После деплоя откройте `https://<ваш-сервис>.onrender.com/health` — должен
   ответить `{"ok":true,...}`.

## Сборка APK (после того как фронтенд будет подключён к API)
Проект — обычный веб-сайт, поэтому проще всего обернуть его через **Capacitor**:
1. `npm install @capacitor/core @capacitor/cli @capacitor/android`
2. `npx cap init "Red Music" "com.example.redmusic"`
3. В `capacitor.config.json` указать `server.url` = адрес задеплоенного на
   Render сайта (`https://<ваш-сервис>.onrender.com`) — тогда приложение
   будет просто открывать боевой сайт внутри WebView, все обновления сайта
   сразу видны в приложении без пересборки APK.
4. `npx cap add android`
5. Открыть папку `android/` в Android Studio → Build → Build Bundle(s)/APK(s) → Build APK(s).
   Понадобится установленный Android Studio с Android SDK.

Могу расписать это подробнее пошагово, когда дойдём до этого этапа.

## OWNER восстановление

При запуске на пустой базе автоматически создаётся OWNER:

- Логин: `owners`
- Пароль по умолчанию: `owner12345`

Для изменения данных можно задать в Render Environment:
- `OWNER_USERNAME`
- `OWNER_PASSWORD`

Существующие аккаунты и данные не удаляются этим механизмом.


### Android icon
The clean Red Music logo is stored in `resources/icon.png` and is used as the Android application icon during the GitHub Actions build. The logo is not displayed in the website header, which remains the `RED MUSIC` text branding.


## APK: воспроизведение музыки
APK открывает боевую версию Red Music через Capacitor WebView. Для воспроизведения
каталожной музыки workflow использует URL backend-сервера. По умолчанию:
`https://red-music.onrender.com`.

Если ваш Render-сервис имеет другой адрес, в GitHub откройте:
Settings → Secrets and variables → Actions → Variables → New repository variable
и создайте `RED_MUSIC_SERVER_URL` со значением полного URL вашего сервиса.

Backend раздаёт загруженные треки через `/uploads` из `STORAGE_DIR/uploads`.


## Важное исправление воспроизведения на новых устройствах

Каталожная музыка теперь загружается из `public/music` по URL `/music/...`, а не из локальной файловой системы владельца. Это позволяет новым пользователям и Android WebView получать один и тот же файл с сервера. Перед сборкой APK положите MP3 каталога в `public/music` с именами из `public/music/README.txt` и отправьте их в GitHub.


## Общая база пользователей

В этой версии регистрация выполняется **сразу через `/api/auth/register`**.
Локальный `localStorage` используется только как кэш интерфейса, а серверная SQLite
база является источником истины.

OWNER может открыть Админ → Пользователи и увидеть пользователей, созданных с
других телефонов/браузеров. Список автоматически обновляется каждые 10 секунд.

### Важно для Render

SQLite-файл хранится в `STORAGE_DIR/data/red-music.db`. Если хостинг очищает
локальную файловую систему после перезапуска/деплоя, SQLite тоже будет очищена.
Для постоянного хранения нужна постоянная файловая система (persistent disk)
или внешняя PostgreSQL/другая база данных.

Сам код уже отделяет базу от интерфейса: переход на внешнюю БД можно сделать
без изменения логики пользователей/ролей.
